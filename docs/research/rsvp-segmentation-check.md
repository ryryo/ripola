# 日本語RSVP研究と実分割の照合

確認日：2026-10-06。現方式は **BudouX 0.9.3のフレーズ分割＋表示上の境界保護**です。短いまとまりを順に表示する点は研究を参考にしていますが、論文と同じ分割器・同じ文節境界を再現した実装ではありません。今回、分割器や保護規則は変更していません。

受入方針はユーザー確認済みです。研究例との完全一致は求めず、自然なまとまりの別解を許容します。`けさ朝顔が／咲きました。`も許容する差です。不自然な切断、極端に長い表示単位、ルビの破壊を重点的に確認し、この例を理由に分割器を交換しません。

## 研究が示す単位と分からないこと

[石森・桐谷（2024）、pp.46–47](https://www.jstage.jst.go.jp/article/jssd/71/0/71_46/_pdf/-char/ja)の図1は「一節ごと」と表記します。これを厳密な文法的文節と同義とは断定できません。本文には解析器、分割アルゴリズム、全刺激の境界列がなく、BudouXとの一致率を計算できません。凝視点誘導・提示速度の研究から、BudouXが最適、あるいは別解析器が必要とは導けません。

[富松（1999）、p.77](https://api.lib.kyushu-u.ac.jp/opac_download_md/4060945/p069.PDF)は自然な発音で区切る最小単位として文節を説明し、「けさ」「朝顔が」「咲きました」の3単位例を挙げます。表示領域の最大12文字は、12文字ずつ機械的に切る規則ではありません。確認した本文から使用解析器・自動切分け手順は特定できず、手作業だったとも断定できません。[DOI](https://doi.org/10.15017/4060945)。

[北名ほか（2025）、方法2.1・考察](https://www.l.u-tokyo.ac.jp/AandC/documents/2025/17.pdf)は1文節ずつの正確な音読を測定しますが、具体的な解析器・分割規則は示されません。音読正答閾値のfpmと、アプリのCPM・句読点休止・自由操作は異なる条件です。分割品質の正解集や速度・理解度の保証には使いません。

## 進行版で取得した境界

[再現スクリプト](../../scripts/report-segmentation.ts)を`node --import tsx scripts/report-segmentation.ts`で実行し、生境界・保護後・UTF-16位置のJSONを保存しました。研究の短い例には比較のため句点を追加しています。青空文庫は元HTMLの読みルビを保持した冒頭3文です。

| 対象 | 実際の表示単位（`／`は境界） | 保護による差 |
| --- | --- | --- |
| 助詞・補助動詞 | 私は／朝の／電車で／本を／読んでいます。 | なし |
| 否定・丁寧・過去 | 彼女は／資料を／読みませんでした。 | なし |
| 日付・数値 | 今日は／2026年10月5日で、／料金は／1,200円です。 | なし |
| 引用 | 彼は／「明日は／晴れる」と／言いました。 | なし |
| 英字・version | TypeScriptで／PDFを／開き、／v2.1の／結果を／比べる。 | なし |
| ルビ付き東京 | 東京へ／行った。 | なし |
| 並列・曖昧性 | 小さな／犬と／猫を／見た。 | なし |
| grapheme | 👩‍💻が／書いたが、／まだ／終わっていない。 | なし |
| 研究の短い例 | けさ朝顔が／咲きました。 | なし。研究の3単位とは不一致 |
| 青空文庫冒頭 | 吾輩は／猫である。／名前は／まだ／無い。／どこで／生れたかとんと／見当が／つかぬ。 | なし |

指定された10例では保護前後の境界は同じでした。既存の自作8例は今回は全て`preferredChunks`と一致しましたが、これらは設計時の表示例です。[既存テスト](../../apps/web/tests/segmentation.test.ts)は本文復元・grapheme・数値・ruby・元位置を検査し、`preferredChunks`／`acceptedAlternatives`との完全一致を合否条件にしていません。8例の一致を文法精度の証明にはできません。「けさ朝顔が」や「生れたかとんと」は、短い文法的文節を必ず返す方式ではないことを示します。

保護が働く別の自作診断例も取得しました。`非常に長い名称`全体をruby親文字とすると、生出力`非常に／長い／名称を／読む。`が、保護後は`非常に長い名称を／読む。`になります。UTF-16位置3・5の境界はruby内部なので除かれます。表示と読みの対応を保つための結合であり、厳密な1文節表示とは異なる例です。11例とも表示単位の連結は抽出本文と完全一致します。

## 実装の制約と次の小さな評価

各ブロックにBudouXを適用した後、grapheme、ruby親文字、URL・email・日付・時刻・数値・英字identifierの内部境界と、独立した句読点・括弧等の境界を削除します。後処理は結合だけで、品詞・係り受け、長さ上限による追加分割、句点直後への強制境界はありません。句読点休止は最終unit末尾で決まり、内部の句読点位置には休止を入れません。source runの区切りも意味上の境界として扱いません。[分割コード](../../apps/web/src/reader/segmentation.ts)、[BudouX上流説明](https://github.com/google/budoux#how-it-works)。

現時点で分割器を交換する根拠はありません。実際に読みにくい箇所を追加し、助詞単独、否定の切断、引用、長いunitを人が確認するのが次の小さな評価です。明確な破損・読書上の問題に限って期待境界の回帰例を追加します。厳密な研究追試が目的なら、著者の刺激・境界列・呈示時間を確認し、別モードとして固定する必要があります。現資料だけでは追試仕様は決められません。
