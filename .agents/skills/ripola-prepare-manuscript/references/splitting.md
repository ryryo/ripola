# 章・節で分割し、元原稿との対応を残す

本棚で探す単位や生成作業の単位を決める手順です。表示フレーズの分割や、providerへ送る合成chunkの分割とは別です。

## 境界を決める

1. 章・節の一覧と各範囲の文字数を調べます。冒頭の目次を本文の章として二重に数えず、Markdown見出しの誤認識を先に直します。
2. 基本は章単位にし、特に長い章は既存の節・番号付き小節を使います。短い導入は続く節へ含めるなど、話の流れを優先します。短い章をそろった文字数にするためだけに分割しません。
3. 聴きたい長さが指定された場合だけ時間を判断材料にします。文字数からの時間は仮の字数/分を明示した概算で、生成・再生の実時間ではありません。
4. 章・節だけでは長すぎる場合は段落境界を使います。文の途中、引用の途中、ルビの親文字や注との対応を切らないようにします。
5. 全体の順番が分かる連番・書名・章節名をタイトルにします。例は`書名 01 はじめに`、`書名 02 第1章 前半`です。本数に応じたゼロ埋めで並び順を保ちます。

入力上限に収まる原稿を必ず分割する必要はありません。1冊として章移動したい用途なら、見出しを整えた単一ファイルも選べます。分割数や特定書籍の構成をプロジェクト共通の固定値にしません。

現在のVOICEVOX/Geminiの標準は文単位の合成で、実験的な自動分割は明示選択です。原稿側を1文1ファイルにする必要はありません。長すぎる1文は、句読点の欠落・OCRの結合を確認します。合成要求の上限を単なるファイル分割で解決したことにしません。[音声chunkの開発契約](../../../../docs/development/speech-chunk-planner.md)を参照してください。

## 対応記録

私的な作業directoryへ、少なくとも次をJSON等の機械可読な形で保存します。

| 項目 | 内容 |
| --- | --- |
| source | 元ファイルの参照、元byte列のSHA-256、文字コード、元の文字数・行数 |
| coordinateSystem | 対応記録で使う座標の単位。例：Unicode code point、0始まり、半開区間 `[start, end)`。アプリのUTF-16とは区別する |
| parts | 順番、出力名、タイトル、元原稿の範囲、整形後文字数、出力byte列のSHA-256 |
| edits | 原本の範囲、変更前後、変更理由。結合・置換・追加を区別する |
| exclusions | 対象外とした目次・図注等の原本範囲と理由 |
| unresolved | 元位置、問題、候補、追加確認が必要な根拠 |

複数の元範囲から構成したパートは範囲の配列で表します。出力文字数から元位置を逆算しません。生成するタイトルや見出しを追加した場合は、原本にない追加として記録します。発音辞書候補も別途残します。

原本座標の検証と整形結果の検証を分けます。まず、全パートの元範囲と除外範囲が原本を順番どおり、重複・未分類の隙間なく覆うことを確認します。次に変更記録を照合し、出力順に連結した本文が、記録した整形・除外・追加から説明できることを確認します。元ファイルのhashが変わっていたら古い対応記録を使いません。

各パートの取り込みプレビューと文字数、境界付近・末尾を確認してから音声化へ渡します。原稿が私的な場合、対応記録や差分も公開リポジトリへcommitしません。
